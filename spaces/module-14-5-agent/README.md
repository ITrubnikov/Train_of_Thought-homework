# Лесоруб через MCP — агент на живой игре Cognopolis (локальный запуск)

Готовый проект к Модулю 14.5 «MCP: универсальный язык tool-сервера» (лекция
на сайте курса). Пуант лекции здесь работает на живой игре: тот же
smolagents-агент, что в проектах 11.5 и 13.6 (реальный API
https://kindomklaster.com, настоящий житель по его под-токену, говорящие
ошибки `{code, message}`, конверт `{result, cooldown, character}`, мозг —
локальная модель из LM Studio), но **в файле агента нет ни одного игрового
инструмента**. В 11.5 и 13.6 `move` / `gather` / `get_map` / `get_character`
были классами в коде проекта (`cognopolis_tools.py`) — теперь их отдаёт
MCP-сервер `cognopolis_mcp_server.py`, а `app.py` про инструменты не знает
ничего: он запускает сервер stdio-подпроцессом и забирает каталог через
`ToolCollection.from_mcp`.

Мозг агента — локальная модель из LM Studio через его OpenAI-совместимый
сервер http://localhost:1234/v1 (ключей не нужно вообще). Конкретную модель
выбирают в выпадающем списке над чатом: «Автовыбор» берёт загруженную в
память (а если ничего не загружено — первую скачанную), либо можно указать
любую конкретную — LM Studio подгрузит её на лету.
Метки в списке: ● загружена, ○ подгрузится при первом сообщении; кнопка
«↻ Обновить» перечитывает каталог (запустили Start server или сменили модель
в LM Studio — видно сразу). Переключение мозга не рвёт MCP-соединение —
подпроцесс сервера зависит от под-токена, а не от модели.

## MCP: что здесь нового против 11.5/13.6

- Контракт лесоруба перестал быть кодом внутри проекта и стал **сервисом**:
  `cognopolis_mcp_server.py` — дословно тот же файл, что лежит в домашке 14.5
  (`notebooks/module-14-5-mcp/mcp-server/cognopolis_mcp_server.py`).
- `app.py` поднимает его подпроцессом — `StdioServerParameters(command=
  sys.executable, args=[cognopolis_mcp_server.py], env={..., COGNOPOLIS_TOKEN})`
  — и делает discovery: `initialize` + `tools/list` по JSON-RPC, всё это
  спрятано внутри `ToolCollection.from_mcp(..., trust_remote_code=True)`.
- Панель «Инструменты из MCP-сервера» показывает каталог, который приехал от
  сервера, а сообщение «Подключено к жителю...» перечисляет его же в чате.
- Соединение открывается при первом сообщении и живёт между сообщениями
  чата; кнопка «Сбросить» и смена токена закрывают его вместе с подпроцессом
  и открывают заново.
- Трейд-офф из лекции виден и тут: `from_mcp` умеет только tools, поэтому
  resource `cognopolis://map` до агента не доезжает — карту он берёт tool-ом
  `get_map` (сервер осознанно держит оба примитива).

## Эксперимент «допиши серверу инструмент»

1. Добавьте в `cognopolis_mcp_server.py` новый узкий tool — например,
   `get_events` из Задачи 3 домашки 14.5 (или свой, любое чтение живого API).
2. Нажмите «Сбросить» и отправьте любое сообщение: в панели «Инструменты из
   MCP-сервера» и в сообщении «Подключено...» появится новый инструмент.
3. Загляните в `app.py`: вы не меняли в нём ни строчки. Клиент видит каталог,
   а не код, — это «контракт, вынесенный в сервис» вживую (зеркало
   эксперимента «убери инструмент» из Блока 3 ноутбука).

## Что нужно, чтобы запустить

1. **Под-токен персонажа Cognopolis** (Character.token вашего жителя —
   копируется в интерфейсе игры на экране «Жители») — его вписывают в поле
   «Под-токен персонажа Cognopolis». Без него агент не работает и ничем не
   подменяется.
2. **Мозг-модель**: запущенный сервер LM Studio (Start server). Загружать
   модель заранее не обязательно — выберите её в выпадающем списке над чатом,
   LM Studio подтянет на лету; берите инструкт-модель с поддержкой tool use
   (в каталоге помечены значком-молотком) и 7B+ — маленькие 4B теряются в
   навигации по карте.
3. **Python 3.10+** — требование `fastmcp`, на котором написан сервер
   (системный python3 на macOS — 3.9, не подойдёт; запасной путь —
   `uv venv --python 3.11`).

## Запуск локально (LM Studio, без ключей для модели)

1. Поставьте [LM Studio](https://lmstudio.ai) и включите сервер (вкладка
   Developer -> Start server). Модель можно не загружать заранее — выберете в
   списке над чатом, LM Studio подгрузит её сама.
2. Из этой папки поставьте зависимости и запустите:

   ```bash
   cd spaces/module-14-5-agent
   python -m venv .venv                # python --version должен быть 3.10+
   source .venv/bin/activate           # Windows: .venv\Scripts\activate
   pip install -r requirements.txt
   cp .env-example .env                # впишите в .env под-токен своего жителя
   python app.py
   ```

3. Откройте http://127.0.0.1:7860 — поле токена уже предзаполнено из `.env`
   (или впишите под-токен руками), выберите модель-мозг в списке и попросите
   «Добудь одно дерево (wood) и вернись домой на (0, 0)».

По умолчанию список ведёт «Автовыбор» — приложение берёт загруженную в память
модель само (а если ни одна не загружена — первую скачанную, LM Studio подтянет
её на лету). Переопределить дефолт можно переменными `LM_MODEL_ID` / `LM_BASE` /
`COGNOPOLIS_BASE_URL` — их же можно вписать в тот же `.env` (он закрыт
`.gitignore`-ом; настоящие переменные окружения важнее).

## Что написать агенту

- «Где стоит мой житель и что у него в рюкзаке?» — чистое чтение: агент зовёт
  `get_character`, приехавший из MCP-сервера, и отвечает по фактам.
- «Добудь одно дерево (wood) и вернись домой на (0, 0), чтобы оно попало на
  склад» — та же задача, что в живом прогоне ноутбука 14.5: маршрут по карте,
  добыча, авто-банк на доме.
- «Разведай карту: где деревья, где камень, где враги?» — сводка по `get_map`
  без единого действия-мутации.

В чате видно каждый шаг цикла think -> act -> observe: какие tools агент
вызвал и что они ответили. Обратите внимание на конверт успешного ответа
`{result, cooldown, character}` и на обучающие ошибки `{code, message}` —
`no_resource_here`, `inventory_full`, `at_map_edge`, `character_on_cooldown`,
`invalid_token`: агент читает message и чинит план сам. После прогона app.py
дописывает «Проверку по факту» — реальные позицию, рюкзак и склад из
`get_character` плюс честный вердикт по дельте склада (сдал ли агент ресурс
на самом деле или только заявил), а не слова модели.

Особенности живого мира (по делу, не по контракту):

- карта поселения 7x7 (`get_map` даёт тайлы `tree` -> wood, `rock` -> stone;
  есть и тайлы с врагами — на них не ходим);
- **отдельного deposit нет**: возврат на дом (0, 0) сам разгружает рюкзак на
  склад (в ответе `move` появляется `banked`);
- **действие ЗАНИМАЕТ время, и по-разному**: шаг ~1 с, добыча и бой ~10 с, крафт —
  десятки секунд (`GET /stats` → `tact.seconds`, длительность рецепта — `GET /recipes` →
  `seconds`). Такт досиживает обёртка: действия в `cognopolis_mcp_server.py` идут через
  `_act`, который спит ровно `cooldown` из ответа;
- мир **общий и персистентный**: житель стоит там, где закончил прошлый раз,
  а не обязательно дома;
- такт зависит от действия: шаг ~1 с, добыча ~10 с, крафт — десятки секунд; ранний повтор отвечает `character_on_cooldown` с
  точным временем ожидания — правило «просто повтори тот же вызов» дано
  агенту в инструкциях;
- добыча за раз может быть больше 1: если на складе поселения лежат
  инструменты (например, топор), `gather` приносит больше — инструменты общие.

Подпорки под слабую локальную модель — те же, что в 11.5/13.6, и по той же
причине: маленькая 7B на живой карте 7x7 сама путает навигацию и пропускает
`get_map` (уходит вслепую к краю и сдаётся). Перед прогоном `app.py` внешней
пробой берёт карту и кладёт прямо в задачу факты о мире (`facts_seed`) и
готовый маршрут до ближайшего дерева (`route_hint`), а после прогона —
честный факт-чек по дельте склада (`fact_check`); всё это в `helpers.py`.
**Важно для урока:** это НЕ игровые инструменты — их агент по-прежнему берёт
только из каталога MCP-сервера. Проба живого API (как и панельный
`_probe_character`) — внешняя разведка мира для человека и для затравки, а не
tool агента; граница модуля цела. На модели посильнее маршрут-подпорку
выключает `WEAK_MODEL_ROUTE=0` — тогда навигацию агент ведёт сам по фактам
затравки и правилам мира из инструкций.

## Сброс

Реальный мир Cognopolis общий и живой — кнопка «Сбросить» его НЕ трогает
(нельзя). Она очищает чат и память агента и закрывает MCP-соединение вместе
с подпроцессом сервера; при следующем сообщении discovery пройдёт заново —
на этом держится эксперимент «допиши серверу инструмент».

## Безопасность токена — и почему он «в двух местах»

Под-токен остаётся в этом локальном процессе и передаётся ровно двум
адресатам: подпроцессу MCP-сервера — через переменную окружения
`COGNOPOLIS_TOKEN` при запуске (в сам протокол MCP токен не попадает) — и,
уже самим сервером, на API игры в заголовке Authorization. Адрес игры
зафиксирован на https://kindomklaster.com; для своего Cognopolis-сервера —
переменная окружения `COGNOPOLIS_BASE_URL` (её читают и панель в `app.py`,
и сервер в подпроцессе).

Может показаться, что токен дублируется: он и у сервера, и у приложения
агента. На деле это один токен из одного источника (`.env` или поле ввода)
с двумя потребителями в разных ролях. Сервер — единственный, кто токен
*использует*: подписывает им каждый вызов игрового API. Приложение держит
его по двум причинам, и обе не про «авторизацию агента»: (1) при stdio
клиент сам запускает сервер подпроцессом — кто-то должен вручить токен его
окружению в момент старта, и это делает приложение; (2) проба токена, панель
«Персонаж (живой мир)» и факт-чек после прогона читают `GET /character`
напрямую, мимо агента, — правду показывает состояние мира, а не слова
модели, и этим прямым чтениям нужен тот же токен. Сама модель (LLM) токена
не видит нигде: ни в промпте, ни в аргументах инструментов, ни в протоколе.
А если сервер запускает чужой клиент (например, `claude mcp add cognopolis
-- python cognopolis_mcp_server.py` с заполненным `.env`) — токен живёт
только у сервера, и агентская сторона о нём не знает вовсе.

## Файлы

- cognopolis_mcp_server.py — MCP-сервер поверх живого API Cognopolis
  (FastMCP): tools `move` (с `Literal` — честный enum в схеме) / `gather` /
  `get_character` / `get_map`, resource `cognopolis://map`, конверт и
  обучающие ошибки как у игры; дословно тот же файл, что в
  `notebooks/module-14-5-mcp/mcp-server/`;
- app.py — модель из LM Studio, `ToolCollection.from_mcp` на stdio-подпроцессе
  сервера, чат на Gradio, поле под-токена, выпадающий список моделей LM Studio
  с кнопкой «↻ Обновить» (наполняется на загрузке страницы через `demo.load`),
  панели «Персонаж (живой мир)» и «Инструменты из MCP-сервера», кнопка
  «Сбросить»; игровых инструментов в нём не определено — в этом весь модуль;
- helpers.py — подпорки под слабую локальную модель (`facts_seed`,
  `route_hint`, `fact_check`), те же, что в 11.5/13.6; чистые функции, к MCP
  и к контракту tools отношения не имеют, на сильной модели файл не нужен;
- requirements.txt — smolagents с MCP-адаптером, fastmcp для сервера и
  клиентские мелочи (openai, requests, gradio).

Мок-лес (`woodcutter_server.py`), discovery руками, эксперимент «убери
инструмент» и подключение клиентов, которые вы не писали (MCP Inspector,
Claude Code), живут в домашке (`notebooks/module-14-5-mcp/` — ноутбук плюс
папка `mcp-server/`) — здесь их нет намеренно: этот проект про тот же MCP
уже на боевой игре.
